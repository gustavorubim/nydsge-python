# M1 regime API and evidence

The M1 boundaries below describe that milestone's revision. M2-M6 are now
completed for fixed-parameter ss104; see [ss104_m6.md](ss104_m6.md). The ss104
wrapper builds its own dated snapshots and belief paths through the M1 kernels.
`smooth_kalman_result(..., data=observations)` adds a Durbin/Koopman conditional
mean/covariance recursion; calls without data retain the M1 RTS path.

M1 supplies deterministic regime paths, finite-duration alternative policies,
and forward information sets. The remaining ss104 equations and calibrations
are the subjects of M2-M5; this milestone does not certify full ss104 parity.

## Public API for a parity harness

Import the following from `nydsge.regimes`:

| Function / container | Purpose |
|---|---|
| `gensys_to_predictable_form(canonical)` | Convert unit forecast-error identities into `Gamma0`, `Gamma1`, `Gamma2`, `C`, `Psi` forward form. Reject unsupported identities explicitly. |
| `gensys2(canonical, terminal, periods=n)` | Backward recursion for `n` temporary quarters; return those transitions followed by the permanent terminal transition. A sequence of canonicals instead permits different equations each quarter. |
| `solve_regime_switching(canonicals, temporary_regimes=...)` | Existing canonical solve per permanent regime; gensys2 per temporary block. Return one `Transition` per regime. Permanent regimes must pass existence and uniqueness. |
| `compute_regime_system(canonicals, measurement_builder, ...)` | Solve, optionally augment, then build regime-specific `TTT`, `RRR`, `CCC`, `ZZ`, `DD`, `QQ`, `EE` and optional pseudo-measurements. |
| `compute_model_regime_system(models, ...)` | Model snapshot wrapper with ordered state/shock/equation/observable index-map validation. Snapshots carry each regime's parameter values and policy equations. |
| `compute_tvis_system(canonical_scenarios, measurement_builder, select_system=..., information_sets=...)` | Solve complete belief scenarios, build measurement rows using each scenario's future path, then select a scenario per realized regime. Supports `scenario_temporary_regimes` for different durations across beliefs. |
| `k_periods_ahead_expectations(transitions, horizon, reg=..., information_set=...)` | Affine forward-state expectation, including ordered products of future `TTT`s and accumulated `CCC`s. |
| `k_periods_ahead_expected_sums(...)` | Sum forward expectations for quarters 1 through `horizon`. |
| `regime_indices_from_dates(regime_dates, dates)` | Map observation dates/quarters to a known regime path. Reject dates preceding the first regime. |
| `RegimeSwitchingSystem(systems, information_sets=...)` | Container with common dimensions; `system[reg]` is a `System`, `system[reg, "TTT"]` is a matrix. |

Regime numbers and scenario selections are **one-based**. Temporary blocks
contain **only temporary regimes**; each block must have an immediately following
permanent regime. For example, `temporary_regimes=((2, 3),)` means two temporary
quarters with regime 4 as the terminal boundary. This avoids DSGE.jl's internal
leading-regime sentinel and `T_switch` indexing convention. Blocks may not overlap
or share temporary terminal boundaries.

Information sets are contiguous ordered regime numbers containing the current
regime. Default `(reg,)` means agents expect today's transition to persist.
`(reg, ..., N)` means agents see the future quarterly path through regime `N`,
then expect `N` to persist. Forward expectations start with the **next** regime.
Temporary/forward-varying regimes must therefore be expanded to one regime per
quarter; historical myopic regimes may span multiple quarters. Multiple belief
scenarios select the whole belief path for measurement expectations, not the
spliced realized path. Credibility-weighted policy equations remain in M4.

`measurement_builder(reg, transition, transitions, information_set)` returns a
`Measurement`; `pseudo_measurement_builder` has the same arguments and returns
a `PseudoMeasurement`. `transition_augmenter(reg, transition)` runs after solving
the complete unaugmented path. A harness can pass upstream canonical matrices and
measurement callbacks without instantiating the unfinished ss104 model.

`nydsge.solve.compute_system` now accepts `regime_models`, `temporary_regimes`,
and `information_sets`. `tvis=True` requires explicit information sets or the
model's `tvis_information_set` setting. `regime_models` and `temporary_regimes`
can also be supplied as model settings. Multi-regime settings without explicit
model snapshots fail instead of silently computing the baseline. Model1002's
measurement/pseudo-measurement builders accept `transitions`, `reg`, and
`information_set`; long rates, long inflation, expected FFR and anticipated GDP
rows use that future path. The default single-regime calculation keeps its
existing arithmetic.

Filter and smooth with the existing public functions in `nydsge.kalman`:

```python
system = compute_system(
    models[0],
    regime_models=models,
    temporary_regimes=((1,),),  # regime 2 is permanent
    tvis=True,
    information_sets=((1, 2), (2,)),
)
indices = regime_indices_from_dates(
    {1: "2020-Q4", 2: "2021-Q1"}, observation_dates
)
filtered = kalman_log_likelihood(
    system, data, regime_indices=indices, log_likelihood_start=presample_periods
)
smoothed = smooth_kalman_result(system, filtered)
observed = observables_from_states(
    system, smoothed.smoothed_states, regime_indices=indices
)
```

Data/state arrays use **periods x observables/states**, unlike Julia's transposed
orientation. Covariances are **periods x states x states**. The filter uses the
first realized regime for stationary initialization, carries state/covariance
across boundaries, preserves partial/all-missing observations and presample
scoring, and allows explicit initial conditions and per-period process covariance
overrides. The smoother saves/uses the filter's regime path and uses `T[t+1]` at
boundaries. Observable and pseudo-observable reconstruction accept the same path.
These are known deterministic regimes, not latent Markov regime inference.

## Verification and boundaries

`tests/test_regimes.py` includes exact array equality for one-regime ss10/ss104
systems, filters and smoothers; two-regime temporary ZLB; a Model1002 policy-row
replacement with augmentation/filtering; different temporary durations; all seven
matrices varying; missing observations; ordered affine expectations; scenario
selection; date mapping; and invalid-input rejection. A stacked Gaussian
conditioning calculation independently checks smoothed means and covariances.

`tests/fixtures/ss104_m1_oracle.json` is an actual small Julia kernel oracle,
generated with Julia 1.12.6 from the pinned source files. It covers gensys2's
two temporary quarters and permanent terminal, all filtered/predicted means and
covariances and period likelihoods with two changing regimes, Hamilton-smoothed
states, and forward expectations/sums. Tests use `atol=rtol=1e-10`.
Regenerate without installing DSGE/particle-filter dependencies:

```text
julia --startup-file=no tools/oracle_julia/export_ss104_m1.jl DSGE_ROOT SSR_ROOT OUTPUT_JSON
```

An additional isolated comparison against the pre-M1 branch head `dc2aaee8`
found **68 arrays bit-identical**: ss10/ss104 with 0/6 anticipated shocks,
all system/pseudo-measurement matrices, likelihoods, predicted/filtered/smoothed
states and covariances. The comparison used an archived source snapshot in
`outputs/pre_m1`; it did not switch branches or modify main.

Remaining gaps: automated ss104 regime dates/parameter mapping and priors (M2+),
COVID equations/volatilities (M2), inflation-error state (M3), flexible AIT and
credibility/two-rule policy equations and calibrated history (M4), full expected
FFR/data wiring (M5), estimator/conditional-forecast orchestration and full
Model1002 ss104 oracle comparison (M6). The existing single-regime CLI workflows
remain supported; the new regime machinery is accessed explicitly through these
Python APIs. No MCMC was run for M1.
